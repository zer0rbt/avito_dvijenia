# AGENTS.md — правила работы над проектом

Читается агентами и людьми перед началом работы. Здесь только то, что
неочевидно из кода и что уже один раз стоило времени.

## Что прочитать перед стартом

1. `README.md` — что это и как запустить.
2. `docs/ROADMAP.md` — план продукта, этапы Э0-Э10, договорённости с заказчиком.
3. `docs/BACKLOG.md` — открытые задачи и вопросы. **Новую задачу пишем сюда, а не держим в голове.**
4. `docs/api_notes.md` — что реально отвечает Avito API на боевом аккаунте.
5. `docs/sources_snapshot.md` — как устроены таблицы поставщика.

## Окружение

- Код живёт в WSL: `/home/zer0rbt/avito_dvijenia`. Python 3.12, venv в `.venv`.
- С Windows-хоста команды идут через `wsl.exe -d ubuntu -- bash -c '...'`.
- Всё рутинное — через `make` (см. `README.md`).

### Экранирование: главные грабли этого проекта

Inline-команды с `$`, кавычками и циклами, переданные через
`wsl.exe -d ubuntu -- bash -lc "..."`, **ломаются молча или странно**.
Реальный случай: цикл `for d in ...; do : > "$d/__init__.py"; done`
потерял значение `$d` и попытался писать в `/__init__.py`, отдав
двенадцать `Permission denied`.

**Правило:** всё, что длиннее одной простой команды или содержит кавычки,
`$`, циклы, heredoc — кладём в `scripts/*.sh` и запускаем файлом.
Одноразовые проверки — тоже (`scripts/check_bot_token.py` как образец).

Файлы редактируем через Write/Edit по пути
`\\wsl.localhost\ubuntu\home\zer0rbt\avito_dvijenia\...`, а не через
`cat > file << EOF` в шелле.

## Безопасность

- **Никогда не коммитим** `.env` и `secrets/`. Оба в `.gitignore`.
  Перед коммитом: `git status`. **Перед `git push` — `make audit`**: он
  проверяет игнор, историю коммитов и ищет в отслеживаемых файлах
  приватные ключи и токены.
- Репозиторий приватный. Это не повод класть в него секреты.
- **Секреты не прогоняем через `api-redirecter`** — там команды и вывод
  идут через общую таблицу открытым текстом.
- `client_secret` Авито был засвечен в переписке — он в бэклоге на
  перевыпуск (`B-006`).

## Принципы, на которых построен код

### Не верить внешним источникам про API

Сторонние клиенты и статьи про Avito API **врут**. Проверено: все источники
писали `GET /token/` — на боевом аккаунте это 404, работает `POST`.

Поэтому в `avito/client.py` у каждого метода стоит маркер:

- `CONFIRMED` — путь совпал минимум в двух независимых источниках **и/или**
  проверен живым вызовом;
- `CANDIDATE` — встречен в одном источнике, живьём не проверялся;
- `UNKNOWN` — не нашли, метод не реализован.

Факт по каждому эндпоинту на нашем аккаунте — в `docs/api_notes.md`,
он перегенерируется командой `make access`.

### Не гадать про то, что нельзя проверить

Если данные нужны, но достоверно получить их нельзя — не подставляем
правдоподобное молча. Заводим явный черновик с флагом и предохранителем,
который **громко падает**.

Образец: `avito/data/categories_draft.yaml` (`verified: false`) +
`avito/categories.py::require_verified()`, который кидает
`CategoriesNotVerifiedError` при попытке опубликоваться на непроверенных
данных.

### Режим оператора не обходить

`core/approval.py` — сквозной предохранитель, а не опция. Причина: боевой
аккаунт с оборотом 200-220к, тестового аккаунта нет, аванс маленький.

- Любая операция, меняющая что-то на Авито, по умолчанию идёт в **dry-run**.
- Боевое исполнение — только после подтверждения оператором в боте.
- `--yes` существует для ручной CLI-отладки. **Планировщик его не использует.**

Новую операцию над Авито заводим через `request_operation()` и регистрируем
исполнителя в `bot/registry.py`. Не зовём Авито напрямую из джобы.

### Отчитываться фактами, а не ожиданиями

Если проверка показала не то, что ожидалось — фиксируем как есть и заводим
задачу. Реальный случай: заказчик назвал аванс ~900 ₽, API вернул 0 ₽.
Это записано в `docs/api_notes.md` и в бэклоге (`B-003`), а не «подкручено»
под ожидание.

## Соглашения по коду

- **Язык**: комментарии, докстринги, документация, сообщения коммитов — русский.
- **Комментарии объясняют «почему», а не «что»**. Особенно там, где логика
  выглядит странно из-за особенностей внешних данных.
- Стиль и импорты держит `ruff` (`make lint`, автопочинка `make fix`).
  Правила зафиксированы явным `select` в `pyproject.toml` — не полагаемся
  на дефолты, они меняются от версии.

## Тесты

`make test`. Гоняем перед каждым коммитом (`make check` = линт + тесты).

- **Парсер внешних данных обязан иметь фикстуру из реального ответа.**
  Не выдуманную — скопированную из живого источника.
  Образец: `tests/test_gsheets.py`.
- **Нашёл баг в разборе данных — пиши regression-тест.**
  Образец: `tests/test_normalizer.py`, тест про `"5000 3850₽"`, который
  наивный парсер схлопывал в `50003850`.
- Тесты, работающие с БД, берут `session` из `tests/conftest.py` —
  это in-memory SQLite, боевой файл не трогается.
- Сеть в тестах не дёргаем: `fetch_csv_rows` и подобное подменяем
  через `monkeypatch`.

## Работа с бэклогом

`docs/BACKLOG.md` — единственное место для задач.

- Нашёл проблему, но чинить сейчас не в скоупе — **заводи запись**, не
  оставляй только `TODO` в коде.
- У записи есть ID (`B-0NN`), приоритет (`P0`-`P2`), этап и колонка «откуда».
  «Откуда» важна: через месяц непонятно, почему задача вообще появилась.
- Закрыл — ставь статус `done` и не удаляй строку, история полезна.

## Git

- Ветка `master`, remote `origin` — приватный GitHub.
- Коммит-сообщение: заголовок одной строкой, потом список того, что
  сделано, **включая найденные по ходу проблемы**. Смотри
  `git log` — там образцы.
- Коммитим по завершении этапа или связного куска, не по одному файлу.
