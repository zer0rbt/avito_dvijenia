## Техдолг

### B-010 · goods_type не определяется автоматически
**Статус:** open · **Приоритет:** P1 · **Этап:** Э2/Э4

`SupplierItem.goods_type` (обувь / верхняя одежда) не заполняется ни одним из
источников — в таблицах этой колонки нет. Без него не выбрать категорию Авито
и не смаппить размерную сетку (у обуви и одежды они разные).

Осложняется тем, что в снимке большинство позиций — худи, футболки, шорты,
костюмы, то есть не «обувь» и не «верхняя одежда» в узком смысле. Нужно
решить, как их раскладывать по категориям Авито — вероятно, через
классификатор по названию плюс ручное доопределение в очереди модерации.

### B-011 · 47 из 82 товаров без опознанного бренда
**Статус:** open · **Приоритет:** P1 · **Этап:** Э2

`guess_brand()` ищет по списку `KNOWN_BRANDS` в `sources/normalizer.py`.
Не опознаются позиции вроде «Утки Поло», «Костюм ОЛД МАНИ», «Джинсы Evisu»,
«Свитер ERD». Бренд нужен для заголовка (`Бренд Модель`) и для подсчёта
отклонений модерации в разрезе бренда.

Не баг: такие товары штатно уйдут в `NEEDS_REVIEW`. Но 47 из 82 — это слишком
много ручной работы, список брендов надо расширять по мере разметки.

### B-012 · Эксперимент: схлопнуть затирку в один проход через DateEnd
**Статус:** open · **Приоритет:** P1 · **Этап:** Э7

Сейчас затирка спроектирована в два цикла Автозагрузки: первый применяет
затёртый контент, второй убирает строку из фида. Возможно, хватит одного —
если отдать затёртый контент вместе с тегом `DateEnd` текущей датой.

Не подтверждено документацией, порядок применения может оказаться обратным
(снимет карточку, не применив затирку, и тогда в архиве останется
распознаваемый товар — ровно то, чего мы избегаем). Проверять **на одной
карточке** на пилоте, не на объёме.

### B-013 · Сеть WSL периодически не достукивается наружу
**Статус:** обойдено, причина не найдена · **Приоритет:** P2

Затрагивает как минимум два независимых направления:

- `httpx` к `docs.google.com` — `[Errno 101] Network is unreachable`, при том
  что `curl` из того же WSL в тот же момент отрабатывает;
- `git push` к `github.com:443` — таймаут после ~120 с, при том что с
  Windows-хоста тот же адрес отвечает 200.

То есть дело не в конкретном источнике, а в сетевом стеке WSL этого окружения
(вероятно, взаимодействие с VPN и IPv6-маршрутом).

Обойдено ретраями: `fetch_csv_rows()` — 3 попытки с бэкоффом,
`scripts/push.sh` — 5 попыток. Работает: последний push прошёл со второй.
Корневая причина не найдена. Если начнёт мешать сильнее — попробовать
принудительный IPv4 в httpx-транспорте и `git config --global http.version HTTP/1.1`.
